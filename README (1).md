# Mini Payment Transaction System

등록 → 수납 → 취소로 이어지는 결제 흐름을 구현한 백엔드 프로젝트입니다.

같은 수납·취소 기능을 **두 가지 트랜잭션 관리 방식**으로 각각 구현하고, 금액을 다루는 시스템에서 꼭 필요한 **멱등성, 동시성 제어, 실패 이력 보존**을 어떻게 처리하는지 비교해 보는 것이 목적입니다.

- 기간: 2026.01 ~ 2026.02
- 인원: 개인

## 기술 스택

| 구분 | 내용 |
|---|---|
| Language | Java 17 |
| Framework | Spring Boot 3.5, Spring Data JPA |
| Database | Oracle 21c XE (Docker), PL/SQL |
| API 문서 | springdoc-openapi (Swagger UI) |
| Test | JUnit 5, AssertJ, Spring Boot Test |

## 두 가지 트랜잭션 방식 비교

| | DB 관리형 | 애플리케이션 관리형 |
|---|---|---|
| API | `/api/payments/pay`, `/api/payments/cancel` | `/api/payments/pay-jpa`, `/api/payments/cancel-jpa` |
| 처리 위치 | PL/SQL 패키지 `PAYMENT_TXN_PKG` | Spring 서비스 + JPA 엔티티 |
| 트랜잭션 | 프로시저 안에서 COMMIT / ROLLBACK | `@Transactional` |
| 호출 방식 | `StoredProcedureQuery`로 IN/OUT 파라미터 전달 | Repository 호출 |
| 상태 변경 | 프로시저 안에서 UPDATE | 엔티티 메서드로 값 변경 후 변경 감지(더티 체킹)로 반영 |
| 결과 | OUT 파라미터(결과 코드, 메시지) | `ProcResult`(결과 코드, 메시지) |

DB 관리형은 프로시저가 트랜잭션을 직접 끝내기 때문에 서비스(`PaymentService`)에 `@Transactional`을 붙이지 않았습니다.

## 주요 구현

### 1. requestId 기반 멱등성

모든 요청에 `requestId`를 받고, `PAYMENT_EVENT.REQUEST_ID`에 UNIQUE 제약을 두었습니다.

- 같은 `requestId`로 이미 성공한 요청이 들어오면 다시 처리하지 않고 `IDEMPOTENT_OK` 반환
- 같은 `requestId`가 다른 종류의 요청에 쓰였으면 `DUPLICATE_REQUEST_ID` 반환
- 네트워크 재시도 등으로 같은 요청이 두 번 와도 중복 수납·중복 취소가 생기지 않음

### 2. 비관적 락으로 동시 처리 차단

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "0"))
@Query("select p from Payment p where p.paymentId = :paymentId")
Optional<Payment> findByIdForUpdateNowait(@Param("paymentId") Long paymentId);
```

- 수납·취소 전에 결제 행을 `SELECT ... FOR UPDATE NOWAIT`로 잠금
- 다른 요청이 이미 같은 건을 처리 중이면 기다리지 않고 바로 `LOCK_FAILED` 반환

### 3. 실패 이력은 별도 트랜잭션으로 보존

처리에 실패하면 본 트랜잭션은 롤백되지만, 실패 이력은 남아야 원인을 추적할 수 있습니다.

- `PaymentEventFailLogger`에서 `Propagation.REQUIRES_NEW`로 실패 이벤트를 따로 커밋
- 본 트랜잭션이 롤백돼도 `PAYMENT_EVENT`에 `FAILED` 이력과 에러 코드·메시지가 남음

### 4. 상태 전이 검증

상태 변경 규칙은 `Payment` 엔티티 안에 두었습니다.

```
UNPAID ──pay──▶ PAID ──cancel──▶ CANCELED
   └──────────cancel──────────────┘
```

- 수납: `UNPAID` 상태에서만 가능, 청구 금액과 수납 금액이 다르면 거절
- 취소: `PAID`는 전액 취소 처리(수납 금액·수납일시 초기화), `UNPAID`는 금액 변화 없이 취소
- 이미 `CANCELED`인 건은 다시 취소할 수 없음

## API

| Method | URL | 설명 |
|---|---|---|
| POST | `/api/payments/issue` | 청구 등록 (`UNPAID` 생성) |
| POST | `/api/payments/pay` | 수납 (DB 관리형) |
| POST | `/api/payments/pay-jpa` | 수납 (애플리케이션 관리형) |
| POST | `/api/payments/cancel` | 취소 (DB 관리형) |
| POST | `/api/payments/cancel-jpa` | 취소 (애플리케이션 관리형) |

요청 예시

```json
// POST /api/payments/pay-jpa
{
  "paymentId": 1,
  "requestId": "PAY-20260201-0001",
  "amount": 1000
}
```

응답 예시

```json
{ "code": "OK", "message": "PAY_SUCCESS" }
```

## 테이블 구조

| 테이블 | 설명 | 주요 컬럼 |
|---|---|---|
| `USER_ACCOUNT` | 사용자 | `USER_ID`, `USER_NO`(UNIQUE), `NAME` |
| `PAYMENT` | 청구·수납 건 | `PAYMENT_ID`, `USER_ID`, `AMOUNT_DUE`, `AMOUNT_PAID`, `STATUS`, `PAID_AT`, `CANCELED_AT`, `VERSION_NO` |
| `PAYMENT_EVENT` | 처리 이력 | `EVENT_ID`, `PAYMENT_ID`, `EVENT_TYPE`(ISSUE/PAY/CANCEL), `EVENT_STATUS`(SUCCESS/FAILED), `REQUEST_ID`(UNIQUE), `ERROR_CODE`, `ERROR_MSG` |

### 테이블 생성 SQL

```sql
CREATE TABLE USER_ACCOUNT (
    USER_ID     NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    USER_NO     VARCHAR2(30)   NOT NULL,
    NAME        VARCHAR2(50)   NOT NULL,
    CREATED_AT  TIMESTAMP      DEFAULT SYSTIMESTAMP NOT NULL,
    CONSTRAINT UK_USER_ACCOUNT_USER_NO UNIQUE (USER_NO)
);

CREATE TABLE PAYMENT (
    PAYMENT_ID   NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    USER_ID      NUMBER         NOT NULL,
    AMOUNT_DUE   NUMBER         NOT NULL,
    AMOUNT_PAID  NUMBER         DEFAULT 0 NOT NULL,
    STATUS       VARCHAR2(20)   NOT NULL,
    CREATED_AT   TIMESTAMP      DEFAULT SYSTIMESTAMP NOT NULL,
    UPDATED_AT   TIMESTAMP,
    PAID_AT      TIMESTAMP,
    CANCELED_AT  TIMESTAMP,
    VERSION_NO   NUMBER         DEFAULT 0 NOT NULL,
    CONSTRAINT FK_PAYMENT_USER FOREIGN KEY (USER_ID) REFERENCES USER_ACCOUNT (USER_ID)
);

CREATE TABLE PAYMENT_EVENT (
    EVENT_ID      NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    PAYMENT_ID    NUMBER          NOT NULL,
    EVENT_TYPE    VARCHAR2(20)    NOT NULL,
    EVENT_STATUS  VARCHAR2(20)    NOT NULL,
    REQUEST_ID    VARCHAR2(100)   NOT NULL,
    AMOUNT        NUMBER,
    CREATED_AT    TIMESTAMP       DEFAULT SYSTIMESTAMP NOT NULL,
    ERROR_CODE    VARCHAR2(50),
    ERROR_MSG     VARCHAR2(4000),
    CONSTRAINT FK_PAYMENT_EVENT_PAYMENT FOREIGN KEY (PAYMENT_ID) REFERENCES PAYMENT (PAYMENT_ID),
    CONSTRAINT UK_PAYMENT_EVENT_REQUEST_ID UNIQUE (REQUEST_ID)
);

-- 테스트용 사용자
INSERT INTO USER_ACCOUNT (USER_NO, NAME) VALUES ('U001', '테스트사용자1');
INSERT INTO USER_ACCOUNT (USER_NO, NAME) VALUES ('U002', '테스트사용자2');
COMMIT;
```

`PAYMENT_EVENT.REQUEST_ID`의 UNIQUE 제약이 멱등성 처리의 기준이 됩니다.

### PL/SQL 패키지 (`PAYMENT_TXN_PKG`)

DB 관리형 API가 호출하는 프로시저입니다.

| 프로시저 | IN | OUT |
|---|---|---|
| `PAY_DB_MANAGED` | `p_payment_id`, `p_request_id`, `p_amount` | `o_result_code`, `o_result_msg` |
| `CANCEL_DB_MANAGED` | `p_payment_id`, `p_request_id` | `o_result_code`, `o_result_msg` |

애플리케이션은 `PaymentProcedureRepository`에서 `StoredProcedureQuery`로 위 프로시저를 호출하고, OUT 파라미터를 `ProcResult`로 받아 응답합니다.

## 테스트

`PaymentFlowIntegrationTest`

- 등록 → 수납 → 취소 전체 흐름: 최종 상태가 `CANCELED`, 수납 금액 0, 이벤트가 ISSUE / PAY / CANCEL 순서로 3건 기록되는지 확인
- 취소 멱등성: 같은 `requestId`로 두 번 취소해도 CANCEL 이벤트가 1건만 남는지 확인

## 실행 방법

1. Oracle 21c XE 컨테이너 실행 (호스트 포트 1522)
2. 위 테이블 생성 SQL 실행 (`ddl-auto=none`이라 JPA가 테이블을 만들지 않음). DB 관리형 API는 `PAYMENT_TXN_PKG` 패키지가 있는 DB에서 동작합니다.
3. 환경변수 설정 후 실행

```bash
export DB_URL=jdbc:oracle:thin:@//localhost:1522/XEPDB1
export DB_USERNAME=<계정>
export DB_PASSWORD=<비밀번호>

./mvnw spring-boot:run
```

서버 포트는 8089입니다. 별도로 배포된 서버는 없으며, 로컬에서 실행한 뒤 Swagger UI(`http://localhost:8089/swagger-ui/index.html`)로 API를 호출해 볼 수 있습니다.
